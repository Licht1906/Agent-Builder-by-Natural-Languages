# Research — MCP integration model: Gmail / Drive / Outlook / Teams

- **Date:** 2026-08-07 (sources accessed this date; token-lifetime figures can drift, re-verify before implementing)
- **Ticket:** #33, child of the wayfinder map #29
- **Purpose:** V2's requirement doc (`VERSION2-REQUIREMENT.md`, "Bảo mật khi Publish") states that when a tool touches an end-user's personal data, the platform must store the OAuth token **per end-user**, not reuse the agent creator's shared credential ("Nếu tool sử dụng dữ liệu cá nhân của từng end-user, lưu credential/OAuth token theo user thay vì dùng chung credential của người tạo Agent"). Gmail, Drive, Outlook, and Teams are exactly this class of tool. This note collects what the MCP spec and each provider's own docs say about auth, so the Tool Definition ticket can design the credential/permission model on primary-source facts rather than assumption.

## 1. Gmail

**MCP server existence.** No MCP server for Gmail ships from `modelcontextprotocol/servers` today, and Google's own MCP catalog (`github.com/google/mcp`) lists managed remote servers for GCP data services (BigQuery, Spanner, Cloud SQL, Cloud Storage, etc.) but no dedicated Gmail server — it only mentions a community/Gemini-CLI-extension style "Google Workspace" server covering Docs, Sheets, Slides, Calendar, and Gmail ([github.com/google/mcp](https://github.com/google/mcp)). The available Gmail MCP servers are third-party/community (e.g. `GongRzhe/Gmail-MCP-Server`), not first-party. **This is a gap**: no official, well-established Gmail MCP server exists as of this research; V2 would need to wrap the Gmail REST API directly (custom MCP server) rather than adopt a first-party one.

**Underlying API OAuth flow.** Gmail API auth is standard Google OAuth 2.0 authorization-code grant (see §5). Scopes are tiered by sensitivity:
- Non-sensitive: `gmail.labels` ("See and edit your email labels")
- Sensitive: `gmail.send` ("Send email on your behalf")
- Restricted (require Google's restricted-scope security assessment if the app stores user data): `gmail.readonly`, `gmail.modify`, `gmail.compose`, `mail.google.com/` ("Read, compose, send, and permanently delete all your email")
(Source: [Gmail API — OAuth scopes](https://developers.google.com/workspace/gmail/api/auth/scopes), accessed 2026-08-07.) Restricted scopes (needed for reading/sending mail) push V2 into Google's CASA/restricted-scope verification process for production use — a real lead-time risk to flag for the Tool Definition ticket, separate from the token-storage model.

**Token refresh mechanics.** Governed by Google's general OAuth 2.0 rules (§5): access tokens are short-lived (`expires_in`, commonly ~3600s), refresh tokens are long-lived and returned only when `access_type=offline` is requested. Google enforces **50 refresh tokens per (client_id, user) pair** — issuing a 51st silently invalidates the oldest — and refresh tokens for Gmail scopes are invalidated if the user changes their password, in addition to explicit revocation and 6-months-unused expiry ([Google — Using OAuth 2.0 to Access Google APIs](https://developers.google.com/identity/protocols/oauth2), corroborated by community-documented behavior; primary confirmation of the 50-token ceiling and 6-month inactivity rule should be re-checked against Google's current "Refresh token expiration" doc before implementation since it wasn't directly quotable during this pass — treat as **medium confidence**, verify at build time).

## 2. Google Drive

**MCP server existence.** The original `modelcontextprotocol/servers` reference implementation included a `gdrive` server (now in the archived reference-servers set), requesting the single scope `https://www.googleapis.com/auth/drive.readonly` and authenticating via a local `node ./dist auth` browser flow that writes credentials to a file on disk, configured through `GDRIVE_OAUTH_PATH` / `GDRIVE_CREDENTIALS_PATH` env vars ([modelcontextprotocol/servers-archived, gdrive](https://github.com/modelcontextprotocol/servers-archived/tree/main/src/gdrive)). Transport is stdio (spawned via `npx`/Docker, consistent with the MCP stdio binding). This reference server is **single-credential-file, single-user by design** — it is not built for multi-tenant per-user token selection; V2 cannot use it as-is and would need to fork it or write a custom server that accepts per-request/per-session credentials instead of a static file path. No first-party Google Drive MCP server exists beyond this archived reference implementation and community forks (`aaronsb/google-workspace-mcp`, `piotr-agier/google-drive-mcp`, etc.).

**Underlying API OAuth flow.** Standard Google OAuth 2.0 authorization-code grant, same token mechanics as Gmail (§5). Drive scopes are tiered:
- Non-sensitive: `drive.appdata`, `drive.file` ("Create new Drive files, or modify existing files, that you open with an app")
- Sensitive: `drive.apps.readonly`
- Restricted: `drive` (full access), `drive.readonly`, `drive.metadata[.readonly]`, `drive.activity[.readonly]`
Google explicitly recommends `drive.file` + Picker API over `drive`/`drive.readonly` where possible, as it needs less verification and gives users per-file consent ([Google Drive API — API-specific auth scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth), accessed 2026-08-07). For an agent-builder where end-users don't interact with a Picker UI at tool-call time, `drive.readonly`/`drive.file` chosen per use case is the likely default; either way this is a restricted scope requiring Google verification for broad read access.

**Token refresh mechanics.** Same as Gmail — shared Google Identity refresh-token behavior (§5): ~1hr access tokens, long-lived refresh tokens subject to the 50-per-(client,user) cap, 6-month inactivity expiry, and revocation on user action.

## 3. Microsoft Outlook (Mail)

**MCP server existence.** Microsoft maintains an official catalog repo, `github.com/microsoft/mcp`, listing first-party MCP servers. It includes **"Microsoft 365 Mail"**, described as a remote HTTP server requiring a tenant ID, alongside a separate "Microsoft 365 Calendar" server and a general "Microsoft 365 Agents Toolkit" local server for M365 app development ([github.com/microsoft/mcp](https://github.com/microsoft/mcp), accessed 2026-08-07). This is the strongest first-party signal among the four services: transport is remote HTTP (i.e. Streamable HTTP per current MCP spec), and it is tenant-scoped, meaning multi-tenant deployment is already part of its design — but per-*end-user* (not just per-tenant) credential handling at call time still needs verification against Microsoft's own server docs before relying on it. Community alternatives wrapping Graph mail (`elyxlz/microsoft-mcp`, `mpalermiti/outlook-mcp`, `Softeria/ms-365-mcp-server`) exist as fallbacks/references if the official server's auth model doesn't fit V2's per-user requirement.

**Underlying API OAuth flow.** Outlook mail is accessed through Microsoft Graph, authenticated via the Microsoft identity platform's OAuth 2.0 authorization-code flow (v2.0 endpoint), same shape as any Entra ID app: shared `client_id`/`client_secret` (or certificate) at the app-registration level, per-user `code` exchange at `/oauth2/v2.0/token` producing a per-user `access_token` + `refresh_token` pair, with `refresh_token` only issued when the `offline_access` scope is requested ([Microsoft identity platform — OAuth2 auth code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow), accessed 2026-08-07). Relevant delegated (per-user, not app-wide) permissions:
- `Mail.Read` — "Read user mail", no admin consent required
- `Mail.Send` — "Send mail as a user", no admin consent required
- `Mail.ReadWrite` — full mailbox CRUD, no admin consent required
(Source: [Microsoft Graph permissions reference](https://learn.microsoft.com/en-us/graph/permissions-reference), accessed 2026-08-07.) All three are **delegated-only** — Graph exposes no meaningful application-permission variant for reading an arbitrary user's personal mailbox without admin-wide consent — which structurally forces per-end-user tokens for this tool, matching the requirement doc directly.

**Token refresh mechanics.** Per Microsoft's docs: access token `expires_in` in the sample response is 3599s (~1hr, tenant-configurable via Conditional Access token lifetime policies). Refresh tokens for confidential web-app clients ("all other scenarios" bucket) default to **90 days**; SPA-flow and email-OTP-flow tokens are capped at **24 hours**. Refresh tokens **rotate on every use** — Entra issues a new refresh token with each `grant_type=refresh_token` call and does not automatically revoke the old one; the client is expected to discard it ([Microsoft identity platform — Refresh tokens](https://learn.microsoft.com/en-us/entra/identity-platform/refresh-tokens), accessed 2026-08-07). Revocation triggers include: user-initiated revocation, admin revocation, password reset (revokes password-based tokens; non-password-based — e.g. OAuth-only — tokens can survive password resets depending on the reset surface used, see the revocation matrix in that doc), and Conditional Access policy changes. Because V2's backend is a confidential client (server-side, holds `client_secret`), the 90-day/rotating-refresh-token path applies — refresh must run periodically (not purely on 401) since 90-day tokens can go stale if unused, though rotation on each refresh call extends effective lifetime indefinitely as long as the platform refreshes at least once every 90 days per user.

## 4. Microsoft Teams

**MCP server existence.** The same official Microsoft catalog lists a **"Microsoft Teams"** remote HTTP server, tenant-scoped like the Mail/Calendar servers ([github.com/microsoft/mcp](https://github.com/microsoft/mcp)). This is a genuine first-party MCP server, unlike Gmail/Drive. Community servers also exist (`hvkshetry/office-365-mcp-server` bundles Teams alongside mail/calendar/planner).

**Underlying API OAuth flow.** Also Microsoft Graph, same Entra ID authorization-code flow as Outlook (§ above, details in §5). Relevant permissions are more mixed between delegated and application scope than mail:
- `Chat.Read` — delegated only, "Read user chat messages" (1:1/group chat on behalf of signed-in user), no admin consent
- `Team.ReadBasic.All` — delegated only, no admin consent
- `ChannelMessage.Read.All` — **both** delegated and application variants exist, and **both require admin consent**
(Source: [Microsoft Graph permissions reference](https://learn.microsoft.com/en-us/graph/permissions-reference), accessed 2026-08-07.) This matters for V2's model: chat/DM access is delegated-only (must be per-end-user), but channel-message access has an application-permission path an org admin could grant once for the whole tenant. If V2 ever needs channel reads independent of which end-user is logged in, that's the one place a shared/tenant-level credential is legitimate rather than a compliance shortcut — everything else in Teams (chat, per-user team list) needs the same per-user token model as Outlook.

**Token refresh mechanics.** Identical mechanics to Outlook — same Entra ID tenant, same token endpoint, same 90-day confidential-client refresh token default with rotation-on-use, same revocation triggers (§3, §5).

## 5. OAuth flow shape and refresh mechanics — shared detail

Both providers use **authorization code grant + refresh token**, which is exactly the shape needed for per-end-user tokens:

- **Google**: app registers one `client_id`/`client_secret` in Google Cloud Console. Each end-user separately visits Google's consent screen (`accounts.google.com/o/oauth2/v2/auth`) and authorizes; the resulting `code` is exchanged server-side for an `access_token` + `refresh_token` pair that is specific to that `(client_id, user)` combination. `access_type=offline` is required to get a refresh token at all; without `prompt=consent` on re-auth, a returning user won't get a *new* refresh token (Google returns the existing one implicitly, i.e. it's typically only issued on first consent) ([Google — OAuth 2.0 for Web Server Applications](https://developers.google.com/identity/protocols/oauth2/web-server), accessed 2026-08-07). Google enforces a **50 live refresh-tokens per (client_id, user)** ceiling — relevant if V2 ever re-issues tokens per environment/session instead of storing and reusing one long-lived refresh token per user.
- **Microsoft**: app registers one `client_id`/`client_secret` (or certificate) in Entra ID. Each end-user authorizes at `/oauth2/v2.0/authorize`; the code is redeemed at `/oauth2/v2.0/token` for a token pair bound to `(user, client)` — Microsoft's docs state explicitly: *"Refresh tokens are bound to a combination of user and client, but aren't tied to a resource or tenant"* ([Refresh tokens in the Microsoft identity platform](https://learn.microsoft.com/en-us/entra/identity-platform/refresh-tokens)), meaning one stored refresh token per (user, Entra app) can mint access tokens for **any Graph resource** that user has consented to for that app (Mail, Teams, Calendar, etc.) — a materially different shape from Google, where scopes are baked into each token's grant more rigidly. `offline_access` scope is required for a refresh token to be issued at all.

Both providers therefore support the requirement directly: **one shared `client_id`/`client_secret` at the platform/app level, N independent per-user authorization-code exchanges, N independent `(access_token, refresh_token)` pairs keyed by user identity** — this is standard OAuth, not something either provider needs to be coaxed into.

## 6. MCP's own auth/credential guidance

The MCP Authorization spec ([modelcontextprotocol.io/specification, Authorization](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization), accessed 2026-08-07) is explicit and directly relevant:

- **Authorization is transport-scoped, not built into the wire protocol generically.** *"Implementations using an HTTP-based transport SHOULD conform to this specification. Implementations using an STDIO transport SHOULD NOT follow this specification, and instead retrieve credentials from the environment."* This means the spec itself pushes stdio-transport servers (the common shape for locally-spawned reference servers, e.g. the archived `gdrive` server) toward **static, environment-supplied credentials** — i.e. one credential per running process, not per-request. This is exactly why the archived Google Drive reference server reads a single credentials file rather than accepting a per-call identity: it's following the spec's stdio guidance, not an oversight, but it also means stdio-mode MCP servers are structurally single-tenant unless the platform spawns **one subprocess per end-user** with that user's token injected into its environment.
- **For HTTP-based transports** (Streamable HTTP, the current standard remote transport per [Transports overview](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports)), the MCP client acts as an OAuth 2.1 client and the MCP server as an OAuth 2.1 resource server. The access token travels as a normal `Authorization: Bearer <token>` **HTTP header on every request** — the spec is explicit that this must happen "even if [requests] are part of the same logical session," i.e. **no session-level static credential caching inside the transport; the token is supplied per request.** This is the mechanism that makes per-end-user tokens practical over HTTP transports: the platform's MCP *client* code (not the MCP server) is what selects and attaches the correct user's Bearer token per call.
- **Confused-deputy protection is spec-mandated.** *"If the MCP server makes requests to upstream APIs, it may act as an OAuth client to them. The access token used at the upstream API is a separate token, issued by the upstream authorization server. The MCP server MUST NOT pass through the token it received from the MCP client."* This is directly relevant to V2's architecture: if V2's own backend issues its own session/access tokens to its MCP client layer, and a downstream MCP server then calls Gmail/Graph, the token used against Gmail/Graph must be the Gmail/Graph-issued per-user token obtained via the flows in §1–4 — **not** a pass-through of whatever bearer token the MCP client presented to the MCP server. The MCP server (or the layer wrapping the raw provider API) is itself acting as an OAuth client to Google/Microsoft, independently of how it authenticates the calling MCP client.
- **No explicit "multi-user MCP server deployment" pattern is prescribed** beyond the above — the spec describes the auth *transaction* (client ↔ resource server ↔ authorization server) per request/session but leaves it entirely to implementers how a single running MCP server process multiplexes many end-users' credentials internally (e.g. keyed lookup by the bearer token's subject claim, or by a custom header). This is the one clear gap V2 has to design itself; official servers with tenant/user scoping (e.g. Microsoft's remote Mail/Teams servers) presumably solve it via Graph's own per-token identity (the Graph token itself, resolved server-side by Microsoft, already carries the calling user — Microsoft's server doesn't need V2 to disambiguate).

## 7. Implications for V2's per-end-user token requirement

**Data model.** A `user_tool_credential` (or `oauth_connection`) table keyed by `(end_user_id, provider)` — not `(agent_id, provider)` or `(creator_id, provider)` — storing at minimum: `provider` (`google` / `microsoft`), `access_token` (encrypted at rest), `refresh_token` (encrypted at rest), `access_token_expires_at`, `granted_scopes`, and, for Microsoft, no `tenant_id` requirement on the credential row itself since Graph refresh tokens are user+client bound, not tenant-bound (§5) — though V2 should still record which Entra tenant authorized, for audit and for handling multi-tenant orgs. One shared `client_id`/`client_secret` per provider lives in platform config (`Settings`/secret store per ADR-0002's existing pattern), never per user or per agent.

**Refresh strategy.** Refresh-on-demand (check `access_token_expires_at` before a tool call, refresh if within a safety margin, e.g. 5 minutes) is simpler and sufficient given short access-token lifetimes (~1hr both providers) — a background refresh daemon adds operational complexity without a clear win at V2's expected scale, and refresh-on-demand also naturally surfaces revocation (`invalid_grant`/`interaction_required`) at the moment a user's agent actually needs the tool, which is when the platform can meaningfully prompt them to reauthorize. One exception worth flagging: Microsoft's 90-day refresh-token lifetime means a user whose agent goes unused for >90 days will hit a dead refresh token: unlike Google (6-month inactivity, effectively less urgent), this is a real "can't refresh on demand because it's already gone" case, so credential rows should probably surface a `last_refreshed_at` health signal and warn creators/end-users when a connection is going stale before it actually breaks, rather than only via 401.

**Selecting the right token at call time.** Given §6's finding that stdio-transport MCP servers are spec-guided toward static, environment-injected credentials, V2 should **not** run one long-lived shared stdio MCP process per tool and try to swap credentials into it per call. The two viable shapes:
1. **Streamable HTTP MCP servers**, where V2's own backend, acting as the MCP client, attaches the correct end-user's Gmail/Graph-derived Bearer token as a per-request header — this matches the spec's explicit per-request token model directly and is the cleaner fit if using Microsoft's official remote Mail/Teams servers (already remote HTTP).
2. **A thin custom wrapper V2 owns** (likely needed for Gmail/Drive regardless, since no first-party remote server exists) that is itself the OAuth client to Google, and is invoked as a library/internal HTTP call per request with the resolved end-user's token passed in explicitly by V2's runtime — i.e. V2's own tool-calling layer resolves `(current_execution.end_user_id, provider)` → token from the credential table → injects it into the outbound Gmail/Graph API call, rather than relying on any generic "MCP server does the OAuth dance" abstraction. This keeps the confused-deputy rule (§6) satisfied by construction: the token used against Gmail/Graph is always looked up from V2's own per-user store, never forwarded from whatever authenticated the calling agent/session.

Given the state of official servers, wrapper-and-resolve (option 2) is likely required for Gmail and Drive either way, and is the safer, more auditable default for Outlook/Teams too even where Microsoft's official remote server exists — until that server's own per-user credential-passing contract is verified against V2's runtime shape.

**Open risks / unknowns.**
- **No official or clearly-dominant MCP server exists for Gmail or Google Drive.** The Drive reference server is now archived and single-user by design; Gmail has no first-party server at all. V2 should plan to build/maintain a thin custom MCP-shaped wrapper for both, budgeted as real engineering work, not "integrate an existing server."
- **Google's restricted-scope verification** (CASA assessment, required for `gmail.readonly`/`gmail.modify`/`drive`/`drive.readonly` when the app stores user data) has real lead time and should be started early if V2 intends to go beyond a small pilot user group — this is a compliance/timeline risk independent of the technical credential model.
- **Microsoft's official remote Mail/Teams/Calendar servers' exact per-user credential-passing contract was not verified in this pass** — the catalog confirms they exist, are remote HTTP, and are tenant-scoped, but the specific mechanism by which a caller identifies "which end-user" per request (custom header vs. token-subject resolution vs. requiring the calling client to already hold a Graph-scoped token) needs a follow-up read of Microsoft's per-server docs before deciding whether to adopt them directly or wrap Graph independently, same as Google.
- **Teams' `ChannelMessage.Read.All` application-permission path** is the one legitimate case in this whole set where a shared, admin-consented, non-per-user credential could be architecturally correct rather than a shortcut — worth flagging explicitly to whoever writes the Tool Definition ticket's permission model so it isn't mistakenly forced into the per-user pattern where it doesn't apply, or conversely used as an excuse to skip per-user tokens where they're actually required (Mail, Chat).
- **The 50-refresh-token-per-(client,user) Google limit** and its exact revocation rules were only corroborated by secondary sources during this pass (Google's live "Refresh token expiration" doc page returned a general OAuth overview rather than the specific limits table) — re-verify directly against `developers.google.com/identity/protocols/oauth2` before hard-coding retry/re-auth logic around it.
